## P3-01 `WondowsConfig` 拼写错误贯穿全局

- **`Editor/Private/Windows/Win32Application.cpp:31`** 及 `WindowHandler.cpp:30,47`

```cpp
Win32Application::Get().WondowsConfig->WindowsSize = int2(newWidth, newHeight);
```

正确拼写应为 `WindowsConfig`。同名的成员、`WondowsConfig` 结构体在多个模块里被引用，现在改名要动很多文件——这正是"趁早改"的理由：越晚成本越高，而且每次读代码都要在脑内多做一次映射。

**建议**：全局替换 `Wondows` → `Windows`，同时修正 `WindowsPostion` → `WindowsPosition`（同一个字段里还有一处拼错）。

## P3-02 局部变量拼写与 API 命名语义错误

- **`Core/Core/Private/Object/ObjectSystem.cpp:30`**：`ObjectHandle Hanedle{...}` 拼写仍在（本轮复核确认未改），建议 → `handle`
- **`Core/Core/Public/Object.h`**：`GetClassHas()` / `GENERATE_CLASS_HAS_*` / `GenerateInformationMap_ObjectTag`

`GetClassHas` 返回的其实是**类名哈希**（`Pipeline/GenerateMetadata.cpp:292`：`std::hash<std::string>{}(className)`；原 `GenerateObjectMetadata.cpp:401` 已随 eb41fb7 搬家），叫 "Has" 完全没有信息量，读代码的人必须去生成器里翻才能明白它是什么。建议改名为 `GetClassHash()`。

## P3-03 `Checker.h` 在全局作用域重定义 Windows 同名符号

- **`Core/Core/Public/Common/Checker.h:7-12, 34-35`**

```cpp
using HRESULT = long;
using UINT = unsigned int;
#ifndef FAILED
#define FAILED(hr) (((HRESULT)(hr)) < 0)
#endif
```

`windows.h` 同样定义 `HRESULT`、`UINT`、`FAILED`。目前靠"类型别名同类型可重复声明 + `#ifndef` 守卫"侥幸共存，但：

- 包含顺序不同（先 `windows.h` 后 `Checker.h`，或反之）时行为不同；
- 某些 SDK 头里 `FAILED` 是有额外语义的宏，被这里覆盖后难查；
- `DISABLE_DLL_WARNINGS_PUSH/POP` 依赖 `__pragma`，只对 MSVC 有效（与 P3-04 同类）。

**建议**：这些别名全部移进 `Core` 命名空间；`FAILED` 只在没有 `windows.h` 时才定义，或干脆用自己的 `HrIsFailed()`。

## P3-04 `__underlying_type` 是 MSVC 专有扩展

- **`Core/Core/Public/Tools/EnumClassFlags.h:5-12, 28, 35`**、**`Checker.h:34-35`**

`__underlying_type(T)` 不是标准 C++，GCC/Clang 不认（标准写法是 `std::underlying_type_t<T>`，C++11 就有）。`__pragma` 同理。README 已经声明"仅 Windows/MSVC"，所以这是"可接受的现状"，但它是**移植的唯一硬阻碍**——如果未来想上 clang-cl 或跨平台，需要先清掉这几处（改动量很小，越早做越好）。

## P3-05 头文件里 `#define` 短宏 + `using namespace`

- **`RenderEditor/Internal/Editor/FileBrowserUI.h:15, 17, 22`**

```cpp
#define literal_root L"Game\\"
using namespace RenderUI;
using namespace AssetPipeline;
```

- `literal_root` 这种无前缀的短宏会污染**所有包含该头文件**的翻译单元，且无法 `#undef` 干净（你不知道别人有没有依赖它）。
- 头文件里的 `using namespace` 会强迫所有包含者接受命名空间合并，是标准的头文件禁忌。

**建议**：改用 `inline constexpr std::wstring_view kGameRoot = L"Game\\";`；`using namespace` 移到 `.cpp`。

## P3-06 两层 `BeginChild` 用了同一个 ID

- **`RenderEditor/Private/Editor/IMGUI_LoggerUI.cpp:122, 127`**

```cpp
ImGui::BeginChild("LogScrollRegion", ImVec2(0, Height), ...);
{
    ImGui::BeginChild("LogScrollRegion", ImVec2(0, 0), ...);   // 同名！
```

ImGui 的 ID 是"父 ID 栈 + 字符串"的哈希。同名嵌套虽然因为父栈不同而不一定冲撞，但一旦外层被 `PushID` 包裹，内外层就会拿到相同 ID，导致滚动状态/焦点被串到一起（表现：滚动条拖外层的，内容跟着动）。这里显然是想写"外层固定高度容器 + 内层滚动区"。

**建议**：内层改成 `"##LogScrollRegionContent"` 或 "LogEntries"。

## P3-07 高度计算的三元/逻辑优先级可疑 + 魔法数字

- **`RenderEditor/Private/Editor/IMGUI_LoggerUI.cpp:120-122`**

```cpp
float RemainingHeight = ImGui::GetContentRegionAvail().y;
float Height = RemainingHeight - 200 > 0 && LogSwitch->detailedInformation ? RemainingHeight - 100 : RemainingHeight;
```

- `&&` 优先级高于 `?:`，所以实际语义是 `((RemainingHeight-200) > 0 && detailed) ? (RemainingHeight-100) : RemainingHeight` —— 逻辑本身"能跑"，但读起来需要查表；
- 魔法数字 `200` 和 `100` 没有任何注释说明它们代表什么（"详情区大约占 100px"？）；
- 当 `RemainingHeight` 在 100~200 之间且 `detailed == true` 时，得到的是 `RemainingHeight - 100`，可能是负数（ImGui 会按 0 处理，表现为详情区被挤没）。

**建议**：改成具名常量 + 显式 `std::max`：

```cpp
constexpr float kDetailReserve = 100.0f;
const float height = LogSwitch->detailedInformation
    ? std::max(RemainingHeight - kDetailReserve, 0.0f)
    : RemainingHeight;
```

## P3-08 `static char` 输入缓冲跨次打开不清空

- **`RenderEditor/Private/Tools/GUI_OpenToolsView.cpp:35`**（配合 `:100-110` 的"新建文件夹"）

```cpp
static char filePath[256] = "";
```

`static` 是为了让 ImGui 输入框在帧之间保持内容（正确），但**弹窗关闭时没有清空**。于是"上次导入的路径"会出现在下一次打开对话框时；新建文件夹名字同理不复位。用户会以为程序记住了什么，或者误用上次路径导入。

**建议**：弹窗关闭（`CloseCurrentPopup` / 确认成功）时把缓冲区 `filePath[0] = '\0'`。

## P3-09 `HWND` 通过 `const char*` + `memcpy` 传递

- **`RenderUI/Private/RenderUI.cpp:293-298`**

```cpp
case encodeToSizeT("HWND"): {
    HWND Hwnd;
    memcpy(&Hwnd, Context.msg, sizeof(HWND));     // Context.msg 是 const char*
    UIContext.hwnd = reinterpret_cast<uintptr_t>(Hwnd);
}
```

发送方（`Win32Application.cpp:94-95`）是 `char buffer[sizeof(HWND)]; memcpy(buffer, &hwnd, sizeof(HWND));`。这套协议：

- 依靠"`const char*` 实际上指向一个 `HWND` 的字节序列"这个约定，无类型无长度；
- 发送方传的是**栈上临时数组**，若接收方改成异步（`PostMessage` 语义）就立刻变悬垂指针；
- 调用方之间没有任何编译期检查，改一下发送端结构就静默读错。

**建议**：`NotificationContext` 里加一个 `union { void* ptr; intptr_t asInt; struct { const void* data; size_t size; } blob; }`，或者干脆为 `HWND` 专用一个 `SetWindowHandle(HWND)` 接口（当前这里就只有一个用途：传窗口句柄）。

## P3-10 两套子系统的 `Priority` 排序方向相反

- **`RenderUI/Private/RenderSubsystem/RenderSubsystemImpl.cpp:50-53`** vs **`Core/Private/Subsystem/Subsystem.cpp:32-35`**

```cpp
// RenderUI：升序
return a.Subsystem->GetPriority() < b.Subsystem->GetPriority();
// Core：降序（"优先级高的先初始化"）
return a.priority > b.priority;
```

同一个 `priority` 概念，两套框架一个"大的先跑"、一个"小的先跑"。任何同时注册到两边的子系统，其 `Init/Uninstall` 顺序都是反的（`Uninstall` 还各自按 `Init` 的逆序，于是两份逆序又互相反转）。另外 `std::sort` 不是稳定排序，同优先级子系统的相对顺序不确定。

**建议**：统一成"数值小 = 先初始化"，并在两处都写注释；同优先级用 `std::stable_sort`。

## P3-11 日志时间戳缺年份，毫秒算出来又丢掉

- **`Core/Logger/Private/LoggerImpl.cpp:107-117`**

```cpp
auto ms = std::chrono::duration_cast<std::chrono::milliseconds>(now.time_since_epoch()) % 1000;  // :110 算完没人用
oss << std::put_time(&tm, "%m-%d %H:%M:%S");                                                     // :115 没有年份
```

- 格式是 `MM-DD HH:MM:SS`，**缺年份**：跨年的日志无法排序/归档；
- `ms` 变量计算了但从未拼接，白白多一次 `duration_cast`；
- 日志文件名（`:119-124`）用的是另一套格式，两处时间格式不一致。

**建议**：`%Y-%m-%d %H:%M:%S`，并把 `ms` 拼进 `".%03d"`。

## P3-14 构建脚本里的路径大小写不一致

- **`Engine/Cmake/common.cmake:16`**：`set(THIRD_PARTY_DIR ${CMAKE_SOURCE_DIR}/Engine/Thirdparty)`
- **`Engine/Cmake/macro.cmake:3, 31`**：`add_subdirectory("Engine/ThirdParty/${ARGV}")`

同一个目录两种大小写（`Thirdparty` / `ThirdParty`）。在 Windows 上因为文件系统大小写不敏感而正常工作；一旦有人用 WSL 挂载、或者在大小写敏感的构建机上跑（CI 容器、Linux 交叉编译），CMake 会报"目录不存在"。

**建议**：统一成 `ThirdParty`（与磁盘上的真实目录名一致），这一条改动只需两行。
