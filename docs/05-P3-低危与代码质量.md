## P3-03 `Checker.h` 在全局作用域重定义 Windows 同名符号

- **`Core/Core/Public/Common/Checker.h:7-12, 34-35`**

```cpp
using HRESULT = long;
using UINT = unsigned int;
#ifndef FAILED
#define FAILED(hr) (((HRESULT)(hr)) < 0)
#endif
```

`windows.h` 同样定义 `HRESULT`、`UINT`、`FAILED`。目前靠"类型别名同类型可重复声明 + `#ifndef` 守卫"侥幸共存，但：

- 包含顺序不同（先 `windows.h` 后 `Checker.h`，或反之）时行为不同；
- 某些 SDK 头里 `FAILED` 是有额外语义的宏，被这里覆盖后难查；
- `DISABLE_DLL_WARNINGS_PUSH/POP` 依赖 `__pragma`，只对 MSVC 有效（与 P3-04 同类）。

**建议**：这些别名全部移进 `Core` 命名空间；`FAILED` 只在没有 `windows.h` 时才定义，或干脆用自己的 `HrIsFailed()`。

## P3-04 枚举标志工具依赖非标准的 `__underlying_type`

- **`Core/Core/Public/Utilities/EnumClassFlags.h:5-12, 28, 35`**、**`Checker.h:34-35`**

该宏与辅助函数使用编译器内建的枚举底层类型查询。可在公共头中包含 `<type_traits>` 并用 C++14 起提供的 `std::underlying_type_t<Enum>`，避免让调用者依赖编译器扩展。

## P3-07 高度计算的三元/逻辑优先级可疑 + 魔法数字

- **`RenderEditor/Private/Editor/IMGUI_LoggerUI.cpp:120-122`**

```cpp
float RemainingHeight = ImGui::GetContentRegionAvail().y;
float Height = RemainingHeight - 200 > 0 && LogSwitch->detailedInformation ? RemainingHeight - 100 : RemainingHeight;
```

- `&&` 优先级高于 `?:`，所以实际语义是 `((RemainingHeight-200) > 0 && detailed) ? (RemainingHeight-100) : RemainingHeight` —— 逻辑本身"能跑"，但读起来需要查表；
- 魔法数字 `200` 和 `100` 没有任何注释说明它们代表什么（"详情区大约占 100px"？）；
- 当 `RemainingHeight` 在 100~200 之间且 `detailed == true` 时，得到的是 `RemainingHeight - 100`，可能是负数（ImGui 会按 0 处理，表现为详情区被挤没）。

**建议**：改成具名常量 + 显式 `std::max`：

```cpp
constexpr float kDetailReserve = 100.0f;
const float height = LogSwitch->detailedInformation
    ? std::max(RemainingHeight - kDetailReserve, 0.0f)
    : RemainingHeight;
```

## P3-08 `static char` 输入缓冲跨次打开不清空

- **`RenderEditor/Private/Tools/GUI_OpenToolsView.cpp:35`**（配合 `:100-110` 的"新建文件夹"）

```cpp
static char filePath[256] = "";
```

`static` 是为了让 ImGui 输入框在帧之间保持内容（正确），但**弹窗关闭时没有清空**。于是"上次导入的路径"会出现在下一次打开对话框时；新建文件夹名字同理不复位。用户会以为程序记住了什么，或者误用上次路径导入。

**建议**：弹窗关闭（`CloseCurrentPopup` / 确认成功）时把缓冲区 `filePath[0] = '\0'`。

## P3-09 `HWND` 通过 `const char*` + `memcpy` 传递

- **`RenderUI/Private/RenderUI.cpp:293-298`**

```cpp
case encodeToSizeT("HWND"): {
    HWND Hwnd;
    memcpy(&Hwnd, Context.msg, sizeof(HWND));     // Context.msg 是 const char*
    UIContext.hwnd = reinterpret_cast<uintptr_t>(Hwnd);
}
```

发送方（`Win32Application.cpp:94-95`）是 `char buffer[sizeof(HWND)]; memcpy(buffer, &hwnd, sizeof(HWND));`。这套协议：

- 依靠"`const char*` 实际上指向一个 `HWND` 的字节序列"这个约定，无类型无长度；
- 发送方传的是**栈上临时数组**，若接收方改成异步（`PostMessage` 语义）就立刻变悬垂指针；
- 调用方之间没有任何编译期检查，改一下发送端结构就静默读错。

**建议**：`NotificationContext` 里加一个 `union { void* ptr; intptr_t asInt; struct { const void* data; size_t size; } blob; }`，或者干脆为 `HWND` 专用一个 `SetWindowHandle(HWND)` 接口（当前这里就只有一个用途：传窗口句柄）。

## P3-10 两套子系统的 `Priority` 排序方向相反

- **`RenderUI/Private/RenderSubsystem/RenderSubsystemImpl.cpp:50-53`** vs **`Core/Private/Subsystem/Subsystem.cpp:32-35`**

```cpp
// RenderUI：升序
return a.Subsystem->GetPriority() < b.Subsystem->GetPriority();
// Core：降序（"优先级高的先初始化"）
return a.priority > b.priority;
```

同一个 `priority` 概念，两套框架一个"大的先跑"、一个"小的先跑"。任何同时注册到两边的子系统，其 `Init/Uninstall` 顺序都是反的（`Uninstall` 还各自按 `Init` 的逆序，于是两份逆序又互相反转）。另外 `std::sort` 不是稳定排序，同优先级子系统的相对顺序不确定。

**建议**：统一成"数值小 = 先初始化"，并在两处都写注释；同优先级用 `std::stable_sort`。

## P3-18 `FindModuleCompileCommand` 的"最优命令"是伪选择，且每个头都遍历全部头补 `-I`

- **`Programs/MagicCodegenTool/Private/Clang/CompileCommands.cpp:286-332`（选择逻辑，`:325-329` 是比较处）；`Private/Clang/AstClassCollector.cpp:237-248`（逐头补模块 `-I`）**

```cpp
size_t bestDirectoryLength = 0;
for (const CompileCommandData& command : commands) {
    ...
    if (moduleRoot.native().size() > bestDirectoryLength) {   // moduleRoot 在同一次调用里恒定
        bestDirectoryLength = moduleRoot.native().size();
        bestCommand = &command;                              // 第一次进来后条件恒为假 → 永远取该模块第一个 .cpp
    }
}
```

- **伪选择**：`moduleRoot` 是循环外算好的常量，`bestDirectoryLength` 第一次赋值后条件就不再成立，所以"最优"实际等于"编译数据库里该模块第一条 `.cpp`"。若同模块里存在带不同 `/D`（例如测试目标）的 `.cpp`，解析用的就是它的开关，结果不确定。
- **O(n²)**：`BuildArgumentsForHeader` 里为了补"生成头所在模块目录"，对**每个头**都遍历 `allHeaders` 调 `AddIncludePath`（`AstClassCollector.cpp:237-248`），而 `AddIncludePath` 内部有 `std::filesystem::is_directory`（且去重判断在 stat 之后），一次全量生成约 2 万次 `is_directory`；`a03a50e` 之后这些调用分散在并行 job 里，单次延迟被掩盖但总 stat 次数不变。

两条都是重构前就有的实现（`5e72262` 只是原样搬运），不构成回归。

**建议**：选择逻辑改成"同一模块内按 `absoluteSource` 与头的公共路径长度取最长"（真正意义上的最近），或干脆"遍历该模块所有 `.cpp` 收集 `/D` 的并集"；`-I` 那一步改成"先把所有模块目录收集一次（去重 + 存在性检查），再对每个头复用同一份列表"。

## P3-19 并行解析的"并行度"日志打的是任务数，缓存校验里有一处恒假判断

- **位置**：`Private/Clang/AstClassCollector.cpp:403`；`Private/MagicCodegenTool.cpp:91-97`

```cpp
Utililitie::Log::Info("Parsing in parallel, number of parallels:" + std::to_string(jobs.size()) + " worker(s)");   // :403
```

`jobs.size()` 是**有待解析内容的头文件数**（当前 8 个），不是 `JobSystem` 实际开的线程数。日志写成 "worker(s)" 会让人误以为并行度可调，排查慢构建时按这个数字判断会走偏；想报真实并行度得问 `JobSystem::GetWorkerCount()`（那条路径本身还有 P2-31 的空判问题）。

同一轮 `220bba3` 在缓存解析里加了：

```cpp
if (ParsedLength != HashText.size() ||
    ParsedHash > std::numeric_limits<uint64_t>::max()) {   // :94-96 —— 恒假
    continue;
}
```

`std::stoull` 的返回类型就是 `uint64_t`，`> max()` 永远不成立；前面 `HashText.front() == '-'` 的过滤也已经排除了负号。两行合起来是"看起来在防御、实际什么也没防"，容易让后来者以为这里已有溢出保护。

**建议**：日志改成 `"Parsing " + std::to_string(jobs.size()) + " header(s) in parallel"`（不承诺并行度），或真的取 `GetWorkerCount()`；把恒假判断删掉，只保留 `ParsedLength != HashText.size()`。

## P3-20 `MCLASS(...)` 后面跟 `//` 注释，标记会静默失效

- **位置**：`Private/Clang/HeaderMacroScan.cpp:170-171`（`ParseMacro` 的收尾校验）

```cpp
if (close == std::string::npos ||
    line.find_first_not_of(" \t;", close + 1) != std::string::npos) {   // 除空白和 ';' 之外的任何字符 → 判定不是宏
    return false;
}
```

也就是说，`MCLASS(MSERIALIZATION) // 这个类会被序列化` 这种写法**不会被识别**：`ParseMacro` 返回 false → 该行不进 `mClassDeclarationLines` → libclang 把类解析出来后又被 `erase_if` 过滤掉 → 这个类在这次生成里彻底消失，而且**全程没有任何日志**（`FindEngineClass` 只会对"识别到 MCLASS 但没有类声明"的情况报错，这里连 MCLASS 都没识别到）。

行尾注释是很自然的写法，建议在收尾校验前先剥掉 `//` 之后的文本（注意不要动字符串字面量里的 `//`），或在"看起来像 MCLASS 但没解析成功"时补一条 Warning。

## P3-21 `QueryCompilerTriple` 在 Windows 上恒失败，且探测失败不缓存

- **位置**：`Private/Clang/CompileCommands.cpp:437-458`（`RunCommandCapture`，`:439-442` 是 `_WIN32` 直接 `return false`）、`:519-548`（`QueryCompilerTriple`）

```cpp
#define ENGINE_CONFIG IO::AbsP::Get().GetEngineDirectory() / u8"Config"
```

宏体是一个**没有外层括号的表达式**，且每次展开都会调用一次 `GetEngineDirectory()`（虽然内部有缓存）。当前所有用法都是 `ENGINE_CONFIG / u8"..."` 这种与 `operator/` 连用的形式，所以没出事；但只要有人写 `ENGINE_CONFIG.string()`、`ENGINE_CONFIG.parent_path()`，或把 `ENGINE_CONFIG` 传给按值取地址/`#ifdef` 之类的语境，就会得到 `path / u8"Config".string()` 这种错误展开。

顺带：文件最后一个 `}` 之后没有换行（`git diff` 会显示 `\ No newline at end of file`），任何按行追加的脚本/合并都会粘到最后一行。

**建议**：改成 `#define ENGINE_CACHE  (IO::AbsP::Get().GetEngineDirectory() / u8"Cache")`，或干脆换成 `inline` 函数（`IO::path EngineConfigDir()`），后者还能被调试器看到；补上文件末尾换行。

## P3-23 生成头直接写最终路径，没有"临时文件 + 重命名"

- **位置**：`Pipeline/WriteMetadataFiles.cpp:37-53`

```cpp
const IO::path outputPath = outputDirectory / (headerStem + L".object.generate.h");   // :37-38
std::ofstream output(outputPath, std::ios::binary | std::ios::trunc);                 // :39-41
...
output.write(metadata.contents.data(), ...); output.close();                          // :46-52
```

写法本身有 `try/catch` 和 `if (!output)` 校验，落盘失败会被收集成错误并让整次生成返回 false（这点没问题）。问题是**目标就是最终路径**：进程在 `write` 中途被杀（Ctrl+C、OOM、断电）时，磁盘上会留下一个截断的 `.object.generate.h`。由于哈希缓存只在全部成功后才写（P2-38 已修），下一次构建会正确地把该头重生成一遍，所以**不会永久残留**；但截断文件在这段时间里会被 clangd/clice 索引、或被人打开查看，表现为"生成头语法错误"。

**建议**：先写 `outputPath + ".tmp"`，`close()` 校验通过后 `std::filesystem::rename` 覆盖目标（Windows 上用 `MoveFileEx(MOVEFILE_REPLACE_EXISTING)` 或先删再 rename）。这样读者要么看到旧版本，要么看到完整新版本。
