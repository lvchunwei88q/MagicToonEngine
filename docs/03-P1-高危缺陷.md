## P1-03 增量缓存解析崩溃：`std::stoull` 无保护

- **位置**：`Programs/MagicHeaderTool/Private/MagicHeaderTool.cpp:67-76`（`std::stoull` 在 `:72`）
- **复核（`738ff16`）**：代码逻辑未变。`MagicConfig.h:7` 的 `MAGIC_DEV` 已从 `1` 改为 `0`，`#if !MAGIC_DEV`（`:147`）包住的增量解析路径**现在已编译进 MHT**，这条崩溃路径当前在线，不再是潜伏状态。

```cpp
for (size_t i = 0; i < FileLine.size(); i++) {
    auto& Line = FileLine[i];
    std::wstring LineW = IO::ToWideString(Line);
    auto[path, time] = SplitInput(LineW);
    size_t time_number = std::stoull(time);   // :72  空串/非数字直接抛 invalid_argument
```

`engine_headers_time_check_file.buildmeta` 是**程序自己生成又自己消费**的缓存。截断写入（上次生成时进程被 Ctrl+C 杀掉，正好落在这个文件上）、手改、末尾多一个空行，都会让 `time` 为空串或非数字 → `std::invalid_argument` → 未捕获 → MHT 崩、构建卡死。

而且它**不是自愈的**：崩溃发生在缓存解析阶段，缓存文件本身不会被重写；下一次构建仍然用同一份坏缓存再崩一次。用户唯一的出路是手动删掉那个隐藏的 `.buildmeta` 文件，而错误日志里没有这句话。

### 修复

```cpp
size_t time_number = 0;
try { time_number = std::stoull(time); }
catch (const std::exception&) {
    Utilitie::Log::Warning("Malformed time-cache line ignored: " + IO::ToNarrowString(LineW));
    continue;   // 跳过坏行，并且因为该文件不在 CheckFiles 里，会重新进 NeedGeneratedFiles → 顺带自愈
}
```

同时对 `SplitInput` 的空 `time` 做前置判断（`time.empty()` → 视为"未缓存"）。

## P1-04 增量判断与产物存在性脱钩

- **位置**：`Programs/MagicHeaderTool/Private/MagicHeaderTool.cpp:51-133`（判断本身）、`:206-229`（`Run()` 的任务循环）
- **复核（`738ff16`）**：逻辑未变，任务数由 `Context::TaskInfo::TaskNum`（`:159`，"每 100 个头文件一个任务"）承载。`MAGIC_DEV` 已改为 `0`，增量判断路径**在线**；与 P1-03 同属"缓存损坏/产物被删就漏生成"这一族。

### 问题

是否需要重新生成的判断只依赖"源码文件的 mtime 是否与缓存里记录的一致"：

```cpp
if (ThisFileModificationTime != CheckFile.time) NeedGeneratedFiles.push_back(fileW);
```

它**不看生成出来的 `.object.generate.h` 是否还在**。于是：

- 删掉 `out/`（或 CI 上换了干净的构建目录，但 `--generate-dir` 指向了持久目录）→ 缓存说"全部没变" → `NeedGeneratedFiles` 为空 → `TaskNum == 0` → `HDDs` 为空 → `Run()` 循环一次都不进、直接 `return true` → **一个头文件都不生成，构建报"找不到 xxx.object.generate.h"**。
- 同样的坑还有 git 切换分支：`checkout` 会把源文件 mtime 设成"现在"，这时反而全部重新生成（正确），但 `git stash`/恢复备份保留旧 mtime 时会漏生成。
- `IO::CreateFile` 对已存在文件会**篡改 mtime**（`FileManager.cpp:162-171`，见 P2-34 与 P2-07 附近），这会额外污染这个判断基准。
- 另一侧同样危险：新代码在 `:115-132` **先把新 mtime 写回缓存，然后才开始生成**（`Run()` 在 `readGenerateInfoFile()` 之后才被调用）。中途失败（异常被吞、Ctrl+C、磁盘满）会让下一次构建认为"已是最新"——见 P2-38。

### 修复

判断条件改成"mtime 变了 **或** 产物不存在"：

```cpp
for (const auto& f : files) {
    ...
    const std::wstring output = ExpectedOutputPath(path, model);   // 与 GenerateMetadataFile 用同一个拼法
    if (!IO::Exists(output) || CheckTime != cachedTime) NeedGeneratedFiles.push_back(fileW);
}
```

并且把 `ctx.GetRefInfo().TaskNum == 0` 显式记一条日志（"nothing to generate: N headers up to date"），避免"静默什么都不做"被当成成功。

## P1-05 注册纹理失败后标志位不复位，`UpdateBuffers` 永久失效

- **位置**：`Runtime/RenderCore/Private/BufferManagerImpl.cpp:66-151`、`:184-189`

```cpp

{
    IsRegisterTextureBuffer = true;                        // :68
    ...
    HRESULT hr = ...CreateTexture2D(...);
    if (FAILED(hr)) { ErrorCapture{}("..."); return; }     // :111-116  ← 未复位
    ...
    if (FAILED(hr)) { ErrorCapture{}("...RTV/SRV..."); return; } // :136-141 ← 未复位
    ...
```

而 `UpdateBuffers` 一进来就先看这个标志：

```cpp
if (IsRegisterTextureBuffer) {
    ErrorCapture{}("Updating the texture buffer is not allowed when registering the texture buffer!");
    return;                                                // :186-189 直接放弃本次更新

```

### 后果

只要有**一次**纹理创建失败（显存不足、格式不支持、尺寸为 0 → 都很常见），标志位就永久停在 `true`：

- 之后窗口每次缩放，`UpdateBuffers` 都不再重建任何非固定尺寸的纹理 → 后处理链/渲染目标停留在旧分辨率；

用 RAII 守卫，保证异常/提前返回也复位：

```cpp
struct FlagGuard {
    std::atomic<bool>& f;
    FlagGuard(std::atomic<bool>& v) : f(v) { f = true; }
    ~FlagGuard() { f = false; }
};
...
FlagGuard guard(IsRegisterTextureBuffer);
```

另外 `:72` 在 `context.Desc` 判空（`:82`）**之前**就解引用 `context.Desc->Width`，是同一族的顺序错误，一起修（见 P2-15）。

## P1-06 子系统初始化失败不回滚 + 错误标志语义反转

- **位置**：`Core/Core/Private/Subsystem/Subsystem.cpp:30-50`

```cpp
SubsystemError SubsystemContextImpl::Init()
{
    for (size_t i = 0; i < Derived.size(); i++) {
        if (!it.subsystem) assert(...);          // Release 下 assert 是空操作 → 下面直接空指针调用
        if (!it.subsystem->Init())
            return {false, it.name.c_str()};     // 失败却把 error 置为 false
    }
    return { true,nullptr };
}
```

### 两个问题

1. **`SubsystemError{false, ...}` 表示失败**，`{true, nullptr}` 表示成功。也就是 `error.error == false` 是**坏消息**。调用方（`MagicEditor/Private/Main.cpp:86`、`MagicLauncher/Private/Main.cpp:40`）正是靠 `if (!error.error)` 判断失败——逻辑能跑通，但任何新人（包括未来的自己）都会读反。这个命名直接导致后面 `IM_ASSERT(false && errorMsg.c_str())` 这类"看不出来到底哪边是错"的代码（P2-27）。
2. **失败后不回滚**：`Init` 走到第 k 个子系统失败就直接 `return`，前面 k-1 个已经 `Init()` 过的子系统既不 `Uninstall` 也没有记录。调用方看到失败就 `return 0` 退出进程 → 那些已初始化的子系统（含 D3D 设备、ImGui 上下文、后台日志线程）没有任何清理逻辑被调用。日志线程是 `std::thread`，进程退出时若还在 join 之外的状态，就是标准库的"terminate on destruction of joinable thread"。

### 修复

```cpp
enum class SubsystemStatus { Ok, Failed };
struct SubsystemError { SubsystemStatus status; const char* subsystem; };

SubsystemError SubsystemContextImpl::Init()
{
    std::sort(...);
    for (size_t i = 0; i < Derived.size(); ++i) {
        auto& it = Derived[i];
        if (!it.subsystem) { /* 记错误 */ return {SubsystemStatus::Failed, it.name.c_str()}; }
        it.inited = true;
        if (!it.subsystem->Init()) {
            // 回滚已初始化的
            for (size_t k = i; k-- > 0; ) if (Derived[k].inited) Derived[k].subsystem->Uninstall();
            return {SubsystemStatus::Failed, it.name.c_str()};
        }
    }
    return {SubsystemStatus::Ok, nullptr};
}
```

同时把 `assert` 换成对所有构建配置都生效的早退 + 错误记录。

## P1-07 Lua 执行：把"栈高"当作"返回值个数"

- **位置**：`Core/Core/Private/LuaVM/LuaVMImpl.cpp:145-158`

```cpp
int status = lua_pcall(Lua, numArgs, numResults, 0);
...
int nresults = lua_gettop(Lua);          // :152  这是整个栈的高度，不是本次返回值个数
if (callback) callback(Lua, nresults);
lua_pop(Lua, nresults);                  // :155
```

### 问题

`lua_gettop` 返回的是**虚拟栈总高**。只要执行前栈上还有任何残留值（例如上一次 `Execute` 的回调里自己压了东西、某个模块把 LuaVM 借去做别的事），`nresults` 就会大于真实返回值个数 → `lua_pop` **多弹** → 栈下溢 → Lua 内部索引校验失败 → `LUA_ERRRUN`/崩溃/后续所有调用错乱。

另外 `numArgs` 目前在公共 API 上**根本无法使用**：`LuaVM` 没有暴露任何"把参数压栈"的接口（只有 `SetGlobal` / `LoadString` / `Execute`），所以 `numArgs > 0` 是一条死路径；要么补上参数接口，要么把这层接口收敛成"无参调用"。

### 修复

```cpp
const int base = lua_gettop(Lua);            // 记录基线
lua_rawgeti(Lua, LUA_REGISTRYINDEX, Rs.Ref);
...
int status = lua_pcall(Lua, numArgs, numResults, 0);
if (status != LUA_OK) { ...; lua_settop(Lua, base); return false; }

const int actual = lua_gettop(Lua) - base;   // 本次产生的值个数
if (callback) callback(Lua, actual);
lua_settop(Lua, base);                       // 恢复到基线，而不是"弹 N 个"
return true;
```

用 `lua_settop(base)` 代替 `lua_pop(n)` 是这类 API 的通用做法：无论回调做了什么，栈都能精确还原。

## P1-08 当前工作目录缓存永不失效

- **位置**：`Core/Core/Private/IO/SystemPath.cpp:36-44`；调用方 `Editor/EngineProject/Private/ProjectControllerImpl.cpp:69`

`AbsolutePath::GetCurrentWorkingDirectory()` 把 `GetCurrentDirectoryW` 的结果缓存在静态变量里（首次调用后就不再取），并提供了 `ClearCache()`，但 `ProjectControllerImpl::SpecifyProJect` 调用 `SetCurrentDirectoryW` 之后**没有**调 `ClearCache()`：

```cpp
// ProjectControllerImpl.cpp 附近
SetCurrentDirectoryW(absolutePath.wstring().c_str());   // :69 返回值也未检查
```

### 后果

- 打开项目后，`GetRoot()` / `Detection` / 文件浏览器里凡是走 `GetCurrentWorkingDirectory()` 的路径拼接，仍然指向**进程启动时的目录**（通常是 `Binary\Debug\`），于是：
  - 项目根判定失败、`Game/` 被解析到错误位置；
  - `project.json` 的查找路径与实际 CWD 不一致（"明明文件在那儿却打不开"）；
  - 是否触发取决于"是否在切目录前调用过 `GetRoot`"——典型的顺序相关 ghost bug。

### 修复

- `SetCurrentDirectoryW` 之后立刻 `AbsolutePath::ClearCache()`（最好把"切目录"封装成一个函数，缓存失效写在里面，避免以后再漏）；
- 更根本的做法：**不要依赖进程级 CWD**，把所有路径都改成基于"项目根绝对路径"拼接。进程 CWD 是全局可变状态，任何第三方库（含 ImGui 文件对话框、Lua 的 `io` 库）都可能改它。

## P1-10 目录遍历抛异常 → 编辑器崩溃

- **位置**：`RenderEditor/Private/Editor/GUI_FileBrowserUI.cpp:184`、`:259`

```cpp
for (const auto& entry : fs::directory_iterator(root)) { ... }                                    // :184
for (const auto& entry : fs::directory_iterator(GetAbsolutePath(state.currentPath))) { ... }      // :259
```

## P1-12 任务投递：任务内再投递会自锁，队列操作无锁

- **位置**：`RenderUI/Private/RenderUI.cpp:309-349`

```cpp
void RenderUIManager::TaskQueue()          // 每帧调用，只处理 1 个任务
{
    m_impl->TaskRun = true;
    if (m_impl->TaskNum <= 0) { m_impl->TaskRun = false; return; }

    TaskFunction Task = std::move(m_impl->FunctionQueue.front());   // :320 未持锁
    m_impl->FunctionQueue.pop();                                    // :321 未持锁
    m_impl->TaskNum = m_impl->FunctionQueue.size();
    Task();                                                         // :323
    m_impl->TaskRun = false;
}

void RenderUIManager::AddTask(TaskFunction Function)
{
    bool IsComplete = false;
    static std::mutex mtx;
    while (!IsComplete)                       // :334 忙等
    {
        std::lock_guard<std::mutex> lock(mtx);
        if (!m_impl->TaskRun.load()) {
            IsComplete = true;
            m_impl->FunctionQueue.push(std::move(Function));
            m_impl->TaskNum = m_impl->FunctionQueue.size();
        }
        if (!IsComplete) std::this_thread::yield();   // :346 空转烧核心
    }
}
```

### 问题

1. **任务内再投递 = 永久死锁（最严重）**。`Task()` 执行期间 `TaskRun == true`，而 `TaskRun = false` 要等 `Task()` **返回之后**才设置（`:326`）。只要 `Task()` 内部调用一次 `AddTask` —— 异步加载完成后安排下一步、任务里刷新数据再投递回调，都是最常见的写法 —— `AddTask` 就会卡在 `while` 里无限 `yield`，而它等的那个标志只有等它返回才会被清 → **UI 线程永久卡死，窗口无响应，且 CPU 占满一核**。
2. **容器操作一半加锁一半不加锁**。`AddTask` 在锁内 `push`，`TaskQueue` 在锁外 `front()/pop()`；`TaskRun` 又是在锁外被置位的，于是 `AddTask` 的"看到 false → push"与 `TaskQueue` 的"置 true → pop"之间存在 TOCTOU 窗口。对同一个 `std::queue` 并发 push/pop 是 UB（内部 `deque` 的指针会被撕裂）。
3. `TaskNum` 是从 `queue.size()` 反推的冗余计数，与队列不同步时 `front()` 会作用于空队列（UB）。
4. 每帧只执行一个任务（`:319-323`），一个大任务（例如加载模型）会把帧率直接拖到个位数——"看起来没卡死，其实每秒 2 帧"。
5. `static std::mutex mtx` 是函数级单例，所有 `RenderUIManager` 实例共享同一把锁；配合上面的自锁问题，等于把整个进程的任务投递都堵在同一处。

### 修复

改成"单所有者 + 每帧快照"，并且明确禁止"任务内同步投递"：

```cpp
void RenderUIManager::Tick() {
    // 1. 锁内只做 swap，锁外执行
    std::vector<TaskFunction> pending;
    { std::lock_guard<std::mutex> lock(taskMtx_); pending.swap(pendingTasks_); }

    // 2. 每帧预算（例如最多 8 个任务 / 4ms），避免大任务卡帧
    const auto deadline = std::chrono::steady_clock::now() + std::chrono::milliseconds(4);
    for (auto& fn : pending) {
        fn();
        if (std::chrono::steady_clock::now() > deadline) { /* 剩下的推回队首，下一帧继续 */ break; }
    }
}

void RenderUIManager::AddTask(TaskFunction fn) {   // 任意线程，永不阻塞
    std::lock_guard<std::mutex> lock(taskMtx_);
    pendingTasks_.push_back(std::move(fn));
}
```

这样 `AddTask` 变成纯入队（不等待、不自旋），任务里再投递也只会排到下一帧，自锁消失。

## P1-13 语言文件缺失或损坏 → 编辑器/启动器起不来

- **位置**：`RenderEditor/Private/Editor/Subsystem_EditorSettings.cpp:47-48`；`RenderLauncher/Private/Subsystem_LauncherGeneralLayout.cpp:32-33`

```cpp
std::string content = IO::ReadAllText(path);   // 文件不存在 → 内部 throw
JSON::parse(content);                          // 语法错误 → nlohmann 抛 parse_error
```

这两处都在子系统 `Init()` 里，没有 `try`。任一语言包被删、被改成非法 JSON、编码损坏，`Init()` 直接抛出：

- `SubsystemContextImpl::Init` 不捕获 → 传到 `MagicEditor::Run()` → 传到 `wmain` → 无 `catch` → 进程终止；
- 用户看到的现象是"双击编辑器，窗口闪一下就没了"，没有任何提示。

### 修复

- 读取 + 解析包一层 `try`，失败时**退回内置默认语言**并记一条警告（语言包不该是启动的必要条件）；
- 结构上更推荐：把"缺文件"和"内容非法"分开处理——缺文件用默认值，非法内容记错误并保留旧值。

## P1-14 `WM_COPYDATA` 载荷无长度校验，可被外部进程触发越界读

- **位置**：`MagicLauncher/Private/Windows/WindowHandler.cpp:30-39` → `RenderLauncher/Private/Subsystem_LauncherGeneralLayout.cpp:62-89`

### 完整调用链

```cpp
// 1) 接收：MagicLauncher/Private/Windows/WindowHandler.cpp:30-39
case WM_COPYDATA: {
    PCOPYDATASTRUCT pcds = (PCOPYDATASTRUCT)lParam;
    if (pcds->dwData == MessageTypeNumber_0 && pcds->cbData > 0) {
        const char* pData = (const char*)pcds->lpData;
        NotifContext Notif{ encodeToSizeT("LOADVALUE"), pData };   // ← 只传指针，cbData 被丢掉
        Core::GetSubsystemContext()->Notification("LAUNCHERDATA", Notif);
        return TRUE;
    }
} break;

// 2) 消费：Subsystem_LauncherGeneralLayout.cpp:62-89
const char* pData = Context.msg;
int nameLen = *(int*)pData;              // 载荷里的第一个 int，完全由发送方决定
pData += sizeof(int);
float percent = *(float*)pData;           // 未对齐解引用
pData += sizeof(float);
std::string name((char*)pData, nameLen);  // nameLen 没有任何上界检查
```

发送端是 `MagicEditor/Private/EnginePreprocessing.cpp:75-87`（把 `int + float + 字符串` 打包，`cbData` 算得是对的），但**接收端在第 1 步就把 `cbData` 丢了**，第 2 步只拿到一个裸指针，于是"发送方 cbData 校验"这层防护等于不存在。

### 问题

1. **越界读**：`nameLen` 由发送方写入，可以是几 MB。`std::string(pData, nameLen)` 会从 `lpData` 开始一直往后读，跨过 `cbData` 边界继续读别人的内存 → 崩溃（读到未映射页）或把任意堆内存内容当成"当前加载资源名"显示在 UI 上（信息泄露）。
2. **未对齐访问**：`*(int*)pData` 假定 `lpData` 4 字节对齐，`WM_COPYDATA` 不保证。
3. **外部可达**：`WM_COPYDATA` 不需要 hook、不需要注入，任何同完整性级别的进程只要 `FindWindowW(ENGINE_LAUNCHER_CLASS, ...)` 拿到句柄就能 `SendMessageW` 发一份伪造载荷（发送端代码里正是这么做的）。这已经不是一个"内部协议"，而是一个**未做输入校验的外部接口**。
4. 发送端也有隐患：`static HWND hTarget = FindWindowW(...)`（`:80`）缓存窗口句柄，启动器重启后句柄失效仍会继续 `SendMessage`（发送到已销毁句柄返回错误但被忽略）。

### 修复

最小改动是把 `cbData` 一起传下去，并在消费前校验：

```cpp
// 接收端
if (pcds->dwData == MessageTypeNumber_0 && pcds->cbData >= (int)(sizeof(int) + sizeof(float))) {
    LoadValuePayload payload{ pcds->lpData, static_cast<size_t>(pcds->cbData) };
    Core::GetSubsystemContext()->Notification("LAUNCHERDATA", { tags, &payload });
}

// 消费端
struct LoadValuePayload { const char* data; size_t size; };
if (payload->size < sizeof(int) + sizeof(float)) return;
int nameLen = 0; std::memcpy(&nameLen, payload->data, sizeof(int));   // 用 memcpy 避免未对齐
if (nameLen <= 0 || static_cast<size_t>(nameLen) > payload->size - sizeof(int) - sizeof(float)) return;
```

更好的做法是换掉这条 IPC：现在它只做"启动器显示加载进度"，用命名管道（带长度前缀）或干脆让编辑器把进度写文件、启动器轮询，都能彻底消除这个攻击面。同时应当只在 `dwData` 校验通过后 `ReplyMessage(TRUE)`（当前直接 `return TRUE`，会打断发送方的 `SendMessage` 同步等待语义之外的路径）。

## P1-15 单元测试与实现矛盾，且从未被执行

- **位置**：`Tests/Core/ObjectTest.cpp:43-47`（测试类）、`:165-178`（断言用例）；生成头 `out/engine_mht_generate/Object/ObjectTest/ObjectTest.object.generate.h:61`；`Engine/Cmake/macro.cmake:98-142`
- **复核（`738ff16`）**：用例仍红。已对照当前生成头确认：`NonSerializableTestObject` 的开关仍是 `Core::ObjectSwitch::Serialization`（`:61`），`Serialize()` 不会抛。新增了 `Tests/LibClang/LibClangTest.cpp` 目标（`Tests/CMakeLists.txt`），但全仓库仍无 `enable_testing` / `add_test`，测试依旧不被 ctest 执行。

### 矛盾推导

```cpp
MCLASS(MSERIALIZATION)                       // 标了"可序列化"
class NonSerializableTestObject final : public MObject {
    GENERATE_BODY(NonSerializableTestObject, Unknown);   // 注意：没有 MMEMBER
};

void ObjectRejectsSerializationWhenDisabled() {
    auto object = ObjectFactory::CreateUnique<NonSerializableTestObject>();
    ExpectThrows<std::logic_error>([&]{ object->Serialize(); });   // 期望抛异常
}
```

`MSERIALIZATION` 会让新流水线生成 `GENERATE_OBJECT_SWITCH_NonSerializableTestObject = Core::ObjectSwitch::Serialization`，并且**同时生成** `SerializeData` 的 cereal 实现（`Pipeline/Ability/GenerateSerializationMetadata.cpp:34-68`，空成员时是 `serialize(Archive&) {}`）。

而 `Object::Serialize()` 只在标志位**没**置上时抛 `std::logic_error` —— 这里置上了，于是 `Serialize()` 一路走到 cereal，**不抛**；`ExpectThrows` 里的 `EXPECT_TRUE(threw)` 失败，该用例报红。

顺带一个反直觉之处：`Object` 基类现在给 `SerializeData` 加了**默认抛异常**的实现（`Object.h:228-233`，"SerializeData not implemented for class: ..."），看起来像"没实现就抛"，但被 `MSERIALIZATION` 的生成体覆盖掉了，所以救不了这个用例。

名字叫 `NonSerializable` 却标了 `MSERIALIZATION`，应改成 `MCLASS(...)` 里不带 `MSERIALIZATION`（或只留空参数）。

### 仍然没被执行

`AddEngineTest`（`macro.cmake:98-142`）虽然现在会产出测试 exe（`ObjectTest`、`LibClangTest` 两个目标），但全仓库 `enable_testing` / `add_test` 一个都没有（grep 确认），`Build.bat` 也不跑 ctest。所以：

- 测试是"编译通过就算过"的装饰；
- 一旦实现改了而测试没同步（就像上面这条），没人会发现；
- 现有用例只覆盖对象序列化与 libclang 解析，核心对象生命周期（注册/删除/槽位复用）完全没有测试保护。

### 修复

1. `NonSerializableTestObject` 去掉 `MSERIALIZATION`；
2. 顶层 `CMakeLists.txt` 加 `enable_testing()`，`macro.cmake` 里加 `add_test(NAME ${TARGET_NAME} COMMAND $<TARGET_FILE:${TARGET_NAME}>)`，`Build.bat` 跑 `ctest --output-on-failure`（失败要让构建真的失败，现在只是打印）；
3. 给 `ObjectSystem` 补一组"注册/删除/复用槽位"的用例——这类问题用 3 行断言就能抓住。

## P1-16 窗口与设备创建失败不检查，继续用空对象

- **位置**：`Editor/Private/Windows/Win32Application.cpp:41-55, 64-99, 101-104`

```cpp
bool Win32Application::Init() {
    ...
    CreateWindows();        // :43  返回类型是 void，失败无法上报

    wc.hbrBackground = CreateSolidBrush(RGB(25,25,25));   // :70 从未 DeleteObject
```

### 后果

- 用户看到的是"启动即闪退"，日志里全是后续错误，缺了"窗口创建失败"这条根因；
- 每启动一次泄漏一个 `CreateSolidBrush` 的 GDI 对象（`:70` 创建，从未 `DeleteObject`）。

```cpp
    if (!CreateDeviceD3D()) return false;
    ...
    return true;
}

bool Win32Application::CreateWindows() {

    if (!::RegisterClassExW(&wc)) { LOG_ERROR(...); return false; }
    HWND hwnd = CreateWindowExW(...);
    if (!hwnd) { LOG_ERROR("CreateWindowEx failed: ", GetLastError()); return false; }
    ...

```

`hbrBackground` 建议直接改成 `(HBRUSH)(COLOR_WINDOW + 1)`，完全不创建画刷；若要保留自定义颜色，则保存句柄并在 `CleanupWindows` 里 `DeleteObject`。
