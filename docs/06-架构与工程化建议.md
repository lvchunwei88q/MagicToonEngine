# 架构与工程化建议

本轮基准为 `49c55d3`。计入 P2-46 修复后，活动清单共 71 项，以下按修复涉及的模块和验收场景组织。

---

## 一、归结出的 8 个根因

### 1. 所有权规则不统一（P2-43、P1-18、P0-03、P2-16、P2-13）

代码里同时存在三种所有权表达：

| 写法 | 出现位置 | 问题 |
| --- | --- | --- |
| `ComPtr<T>` | `BufferManagerImpl`、`RenderRTImpl` | 到处 `.Get()` 出裸指针，再**手动** `Release()`（P0-03） |
| 裸指针 + 手动生命周期 | `ObjectSystem::Objects`、`TextureBuffer::InitialData.pSysMem` 混用 | 谁负责释放不明确 |
| 宏生成的所有权转移 | `RS_REGISTER_METHODS` 里 `new FunctionArray()` + `delete Subsystem->Array` | 谁 new 谁 delete 靠约定 |

**建议**：定一条硬规则并写进代码规范——

> 任何 COM 对象只允许被 `ComPtr` 持有，禁止对 `.Get()` 的结果调用 `Release()`/`AddRef()`；需要转移所有权时用 `std::move`；需要"借用"时把参数类型写成 `T*`（明确不接管所有权）。

配套做法：在 CI 里加一条 grep 检查（对 `.Get()->Release()`、`.GetAddressOf()` 出现在非常规位置的情况报错），成本极低。

### 2. 没有异常边界（P1-10、P1-13、P1-06、P2-07、P2-08；P1-03 已随 `5ad6ae7` 修掉）

现状是"处处 `throw`"，只是最近才开始收口：

- `IO` 层所有函数（`ReadAllText`/`WriteAllText`/`MoveFile` 部分）在失败时 `throw`；
- `JobSystem` 现在有了**一层兜底**：`ExecuteTask`（`JobSystem.cpp:156-172`）捕获任务异常并交给 `ErrorCapture`，异常不再逃出线程入口（P2-32 已修）。但这只是"不崩"，任务失败对调用方**依旧不可见**——`JobHandle` 没有失败标志，计数器照常归零；
- `ErrorCapture` 的接收者只有编辑器在 `Editor.cpp:15-21` 注册；MagicCodegenTool 没注册，Release 下捕获到的错误直接丢进 `((void)0)`（`CoreMinimal.cpp:18-32`，`LOG_OUTPUT` 在 `:8-16`，只有 `_DEBUG` 才有输出）；
- 渲染/UI 主循环、`Subsystem::Init`、进程入口仍然没有 `try`；
- 于是任何"文件缺失 / JSON 损坏 / 设备丢失 / 打不开的源文件"仍然等价于**进程消失**。

**建议**：定义三级异常策略，不要一刀切：

1. **框架边界（必须有）**：`wmain`、每帧 `Tick`、每个子系统 `Init/Uninstall`、每个并行 worker 入口，各加一层 `try/catch` + 错误记录。这一层只保证"不崩、有日志"。`JobSystem` 的 worker 入口已经做了，其余三处还没有。
2. **可预期的失败（用返回值）**：IO、JSON 解析、资源加载、命令行参数，改成 `expected<T> / bool + error` 风格，不用异常表达"文件不存在"这种常态。`MagicUtilities::ReadFilesParallel` 已经改成了 `bool + errors`，可作为模板。
3. **编程错误（保留异常/断言）**：空指针、状态机违例，可以 `throw` 或 `assert`，但必须落在第 1 层的边界内。

### 3. 并发模型没有定义（P1-12、P2-02、P2-12、P2-13、P2-14、P2-31）

- `JobSystem` 没有任务取消、没有异常传播通道、没有"关闭时排空队列"；
- `RenderUI` 的跨线程任务队列是"裸 `std::queue` + 忙等"；
- `BufferManager` 一部分路径加锁、一部分不加；
- `Logger` 有两把锁，其中一把被注释掉；
- `Object::GetNextId` 用非原子自增。

**建议**：明确"谁拥有哪份数据、谁只能读"。

| 数据 | 归属线程 | 其他线程访问方式 |
| --- | --- | --- |
| D3D 设备/上下文/缓冲区表 | 渲染线程（唯一） | 通过"任务队列"投递，不直接调用 |
| 日志条目 | 任意线程写 → 日志专用线程刷盘 | 双缓冲 + 锁（或 `moodycamel` 之类无锁队列） |
| 对象登记表 | 任意线程（有锁） | 只读快照 |
| 子系统表 | 主线程 | `Init/Uninstall/Notification` 都只在主线程 |

有了这张表，P1-12/P2-13/P2-14 怎么修就自然是"按表实现"，而不是逐个打补丁。

### 4. 全局可变状态（P1-08、P2-19、P2-20、P2-27、P2-29）

- 依赖进程 CWD，并且在切目录时不失效缓存；
- 生产入口里跑测试、写死 `D:\Test\MTE`；
- 启动器的项目列表写死 JSON；
- 字体路径写死 `c:\Windows\Fonts\msyh.ttc`（`RenderUI.cpp:225` 附近）。

**建议**：引入一个"运行时上下文"（`EngineConfig`），只允许两处写、其余只读：命令行解析处 + 项目打开处。所有路径通过 `EngineConfig::ProjectRoot()` 拼，禁止任何模块直接调 `GetCurrentDirectoryW` / 写死盘符。

### 5. 增量构建的"确定性"没完全建立（P1-04、P2-22、P2-34、P2-37、P2-42）

`MagicCodegenTool` 是整条构建链上最关键的自研工具。复核 `5e72262`：流水线已接入 libclang AST 解析、解析代码已拆进 `Clang/` 子目录（`5e72262`），N² 并发写盘已拆掉，输出目录按模块拆分（P2-37 部分缓解），读文件侧已改成"收集错误 + 返回 `bool`"（P1-02 已修），编译数据库按 `--generate-dir` 拼固定路径，**增量判据已从 mtime 换成文件内容 FNV-1a 哈希**（`5ad6ae7`，P2-38 整条修掉、P1-03 修掉）；下面几条缺口仍在：

- **不确定**：`ClassId` 来自 `GlobalAutoincrementedValue()`（`GenerateMetadata.cpp:254-257`，进程内 `static` 自增），分配顺序仍取决于 `std::unordered_set` 的遍历顺序（`:263,268`）；`GetClassHas` 来自 `std::hash<std::string>`（`:296`，标准未规定实现）。类名清单已用 `std::map` 排序（`:290`），部分顺序问题被缓解，但 unordered_set 遍历与 `std::hash` 仍是不确定源。同一份代码在不同机器/不同 STL 上可能生成不同的 id —— 一旦这些 id 落进序列化数据，资产就跨机器不可读。
- **不完整**：增量已改成内容哈希，`touch` 源码不再误触发；**但产物存在性依旧不参与**（P1-04）。哈希表在 `MagicGlobalContext` 里攒着、等全部任务成功才由 `Run():243-245` 落盘，失败不更新——"先落盘后生成"那个口子（P2-38）已经收干净。
- **不安全**：读文件侧已不再裸抛（`30beaee`），但任务体本身没包 `try/catch`，`resize`/`ToNarrowString` 抛出的异常会被 `ExecuteTask` 吞掉、`errors[index]` 仍为空，函数返回 true、内容为空 → MagicCodegenTool 带着空头文件继续生成（见 07 第 7.3 节）；同模块同名头文件仍会撞生成路径（P2-37 残留）。
- **开关耦合**：`MAGIC_DEV`（`MagicConfig.h:7`）一个宏同时控制调试日志、整条增量路径、以及"缓存内容有没有被赋值"（P2-36）；当前值已是 `0`、增量在线。`5ad6ae7` 之后第三层含义更硬：`SetHeaderHashCheckContents` 的唯一调用点在 `FilterFilesNoNeedGenerated()` 里，而该函数被 `#if !MAGIC_DEV` 包着，于是 `MAGIC_DEV = 1` 时 `Run()` 收尾必定判缓存无效、报错返回 false（P2-41）——与磁盘上有没有缓存文件无关，"改个日志开关"就等于"让任何 DEV 构建失败"。
- **模块标识两套口径**：`engine_headers.buildmeta` 用 CMake 目标名当模块标识（`CORE`/`LOGGER`/`RENDERCORE` 是大写目标名），而 `FindModuleRoot`（`Clang/CompileCommands.cpp:98-117`）按目录名精确比较（`Core`/`Logger`/`RenderCore`）——40 个头因此永远拿不到模块根，这三个模块里出现第一个 `MCLASS` 类就会报 `No compile command found` 并中断整次生成（P2-40）。同一套名字还被用来拼 `Object/<模块名>` 输出路径，口径不统一迟早还会在别处咬人。
- MSVC 解析参数对分离式强制包含的处理仍有遗漏。P2-46 的启动器和版本化驱动识别已修复，强制包含选项仍按 P2-42 跟踪。

**建议**：

1. `ClassId` / `ClassHash` 改成**由类名确定性推导**（如 FNV-1a 64 位或 SHA-1 截断），彻底摆脱遍历顺序与工具链；
2. 生成的 id 表额外输出一份 `.idmap.json`（类名 → id），作为**可 diff、可 review** 的产物纳入版本管理；id 冲突在生成期直接报错；
3. 增量判断再补后半截：输入用"源码内容哈希 + 工具版本 + 参数哈希"，输出校验"`<generateDir>/Object/<module>/<stem>.object.generate.h` 存在"（`5ad6ae7` 只做了输入侧）；
4. 解析链路把 `INCLUDE` 缺失变成**前置显式报错**，并把 `/utf-8`、`/permissive-`、`/MD` 一并透传，别让每个头各自报一串 `file not found`（P2-42）；
5. 写文件统一"临时文件 + 原子替换"。

### 6. 没有质量保障回路（P1-15；仍缺对象生命周期回归用例）

- 现有两个测试目标：`ObjectTest`（对象序列化，其中 1 个用例与实现矛盾、仍是红的）与新增的 `LibClangTest`（libclang 解析）；
- `Tests/Common/TestFramework.h`（原名 `Test.h`）搭了一套自研 runner（`EXPECT_*` / `ExpectThrows` / `TEST_MAIN`），`AddEngineTest`（`macro.cmake:97-127`）也会产出可执行文件，但 `add_test` / `enable_testing` / ctest 一条都没接，测试仍然从不执行；
- 没有任何形式的 CI / 冒烟脚本（例如"启动编辑器 3 秒后截图"）。

至少补三类测试，它们正好能抓住本报告里的高危项：

| 测试 | 能抓住 |
| --- | --- |
| `ObjectSystem`：注册 3 个 → 删中间 → 再删尾部 → 断言计数与句柄一致 | 对象生命周期 / 句柄一致性 |
| 反复加载纹理再清空资源并解绑，检查 D3D11 活动对象 | P2-43 |
| `MagicCodegenTool`：连续跑两遍，断言生成的 `.h` 逐字节一致 | 确定性 id |

### 7. 平台与图形 API 的表述超前于实现（README、Launcher）

- README 声明"仅 Windows x64"，但代码里的 `__underlying_type`、`__pragma`、`Win32Application` 全是 MSVC/Win32 专有 —— 这不是问题，问题是**没有在代码层面显式约束**（缺少 `static_assert(sizeof(void*) == 8)`、缺少 `#ifdef _MSC_VER` 的明确报错）。
- Launcher UI 里有 "DX12/DX11" 选项，但 `RenderCore` 里只有 DX11 设备创建路径 —— 选择 DX12 会走到不存在实现的分支（有用户会以为支持）。
- README 列了 `Vulkan SDK`、`DirectXShaderCompiler`、`SPIRV-Cross`，但当前代码没有引用任何 Vulkan 或 DXC 的入口 —— 属于"依赖表超前于实现"。

**建议**：要么把选项做成"占位并置灰 + tooltip 说明未实现"，要么从 UI 里去掉；README 的依赖表标注"已使用 / 预留"。

### 8. 文档与脚本漂移（P3-13 部分修复）

`README` 文件树里仍列着不存在的 `GenerateVSProject.bat`（`README.md:94` / `README.en.md:94`，正文那段说明已删除，但文件树没跟着改）、`ThirdParty/` 仍被画在根目录（`README.md:89`，实际在 `Engine/ThirdParty`）、`CMakeLists.txt:51-52` 注释与实际不一致。`Build.bat` 此前"构建前清空 Ninja 缓存目录"的逻辑已删除（改为复用增量目录）。`Engine/Cmake/common.cmake:16` 的 `Thirdparty` 大小写已在 `19eb464` 统一为 `ThirdParty`（P3-14 已修）。
第七轮（`e2e45d2..5e72262`）里文档侧有一次**大规模同步**：`25c6bb1` / `480b1f4` 把全部术语 `MagicHeaderTool` → `MagicCodegenTool`、生成目录 `out/engine_mht_generate` → `out/engine_codegen_generate` 一起改掉了，`docs/` 与两份 README 都已跟上，所以"术语不一致"这一类问题现在没有残留；`MagicCodegenTool.cpp` 里那条路径重复的错误信息（`engine_generate_info…` 拼两遍）也随 `5ad6ae7` 一起消失。剩下的仍是**文件树/注释与实际不符**这种"改代码不改文档"的老问题。
**建议**：把 `README` 的"构建"章节当成**可执行脚本的说明**来维护——每加一个 `.bat` 就同步改 README，并在 CI 里加一条"README 提到但仓库不存在的文件"检查（非常便宜）。另外 `5e72262` 之后 `Programs/MagicCodegenTool/` 多出一层 `Clang/`（`AstClassCollector` / `CompileCommands` / `HeaderMacroScan` / `ClangOwnership` / `ClangPathUtility`），README 或 docs 里的目录说明也该跟着长出来。

## 三、几个需要你决策的问题

这几处不是 bug，而是设计取向，改法差别很大，建议先定方向再动手：

1. **`ObjectSystem` 要不要保留"数组 + 索引"的结构？**
   如果未来需要"遍历全部对象"（序列化整个场景、GC、调试面板），现在的 `vector + swap` 是行不通的，建议直接换成 `unordered_map<id, object*>` + 稳定 id；如果永远只需要计数，那至少要修 swap 的句柄同步。

2. **异常还是错误码？**
   当前 IO 层全是异常。如果倾向"错误码/`expected`"，改动面很大（几十个调用点），但换来的是"任何失败都可控"。如果倾向"保留异常"，那么第 1 批里的框架边界就是唯一防线，必须做扎实。

3. **DX12 是计划内的吗？**
   如果是，`RenderCore` 现在这种"全局 `RenderContext` 单例 + 直接 DX11 类型"的结构基本要重做（`BufferManager` 的接口里到处是 `ID3D11*`）。如果短期不做，建议把 UI 里的选项去掉，避免给使用者错误预期。

4. **`MSVC` 专有依赖要不要清？**
   `__underlying_type` / `__pragma` / `DISABLE_DLL_WARNINGS` 这几处清理成本很低（半天），清掉之后至少 `clang-cl` 能编，对 IDE 体验和静态分析都有好处。要跨平台则需要更大投入。

## 四、本次审查的边界（请一并知悉）

- 前七轮的主要依据是**静态阅读**：首轮通读全仓库，之后六轮（`eb41fb7..738ff16`、`738ff16..19eb464`、`19eb464..f0d41ad`、`f0d41ad..35a05bf`、`35a05bf..e2e45d2`、`e2e45d2..5e72262`）只重读了被提交改动过的文件，未变更条目沿用前轮结论；没有全量编译、没有运行、没有跑测试。因此"必然崩溃"类结论（P0）我给了触发条件；如果实际运行中未复现，请按正文描述的条件去构造。
- 没有覆盖 `Engine/ThirdParty` 的第三方库本体（ImGui、cereal、ufbx、Lua、nlohmann、libclang 等），也没有审计 `Engine/Content` 下的资源。
- 没有做性能实测（P2 里的性能条目是基于代码结构的判断，不是测量结果）。若要量化，建议先用 `RenderDoc` 抓一帧 + `Very Sleepy`/`ETW` 采样，再决定优化优先级。
- 第八轮以 `49c55d3` 为基准，增量 ID 的隔离验证与其余静态推导见复核记录第十二节。
