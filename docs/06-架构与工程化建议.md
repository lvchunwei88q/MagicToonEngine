# 架构与工程化建议

这份文档不是重复缺陷清单，而是把 68 条缺陷**归因**到几个结构性问题，并给出可执行的修复路线。看完 02~05 的具体条目之后，建议按本文的顺序推进。

---

## 一、归结出的 8 个根因

### 1. 所有权规则不统一（P0-01、P0-03、P0-02、P2-16、P2-13）

代码里同时存在三种所有权表达：

| 写法 | 出现位置 | 问题 |
| --- | --- | --- |
| `ComPtr<T>` | `BufferManagerImpl`、`RenderRTImpl` | 到处 `.Get()` 出裸指针，再**手动** `Release()`（P0-01、P0-03） |
| 裸指针 + 手动生命周期 | `ObjectSystem::Objects`、`TextureBuffer::Texture` 混用 | 谁负责释放不明确 |
| 宏生成的所有权转移 | `RS_REGISTER_METHODS` 里 `new FunctionArray()` + `delete Subsystem->Array` | 谁 new 谁 delete 靠约定 |

**建议**：定一条硬规则并写进代码规范——

> 任何 COM 对象只允许被 `ComPtr` 持有，禁止对 `.Get()` 的结果调用 `Release()`/`AddRef()`；需要转移所有权时用 `std::move`；需要"借用"时把参数类型写成 `T*`（明确不接管所有权）。

配套做法：在 CI 里加一条 grep 检查（对 `.Get()->Release()`、`.GetAddressOf()` 出现在非常规位置的情况报错），成本极低。

### 2. 没有异常边界（P1-02、P1-03、P1-10、P1-13、P1-06、P2-07、P2-08）

现状是"处处 `throw`"：

- `IO` 层所有函数（`ReadAllText`/`WriteAllText`/`MoveFile` 部分）在失败时 `throw`；
- `JobSystem` 明确不捕获（注释还写着"让它传播"）；
- 渲染/UI 主循环、`Subsystem::Init`、进程入口全部没有 `try`；
- 于是任何"文件缺失 / JSON 损坏 / 设备丢失 / 打不开的源文件"都直接等价于**进程消失**。

**建议**：定义三级异常策略，不要一刀切：

1. **框架边界（必须有）**：`wmain`、每帧 `Tick`、每个子系统 `Init/Uninstall`、每个并行 worker 入口，各加一层 `try/catch` + 错误记录。这一层只保证"不崩、有日志"。
2. **可预期的失败（用返回值）**：IO、JSON 解析、资源加载、命令行参数，改成 `expected<T> / bool + error` 风格，不用异常表达"文件不存在"这种常态。
3. **编程错误（保留异常/断言）**：空指针、状态机违例，可以 `throw` 或 `assert`，但必须落在第 1 层的边界内。

### 3. 并发模型没有定义（P1-12、P2-02、P2-12、P2-13、P2-14、P2-31）

- `JobSystem` 没有任务取消、没有异常传播通道、没有"关闭时排空队列"；
- `RenderUI` 的跨线程任务队列是"裸 `std::queue` + 忙等"；
- `BufferManager` 一部分路径加锁、一部分不加；
- `Logger` 有两把锁，其中一把被注释掉；
- `Object::GetNextId` 用非原子自增。

**建议**：明确"谁拥有哪份数据、谁只能读"。

| 数据 | 归属线程 | 其他线程访问方式 |
| --- | --- | --- |
| D3D 设备/上下文/缓冲区表 | 渲染线程（唯一） | 通过"任务队列"投递，不直接调用 |
| 日志条目 | 任意线程写 → 日志专用线程刷盘 | 双缓冲 + 锁（或 `moodycamel` 之类无锁队列） |
| 对象登记表 | 任意线程（有锁） | 只读快照 |
| 子系统表 | 主线程 | `Init/Uninstall/Notification` 都只在主线程 |

有了这张表，P1-12/P2-13/P2-14 怎么修就自然是"按表实现"，而不是逐个打补丁。

### 4. 全局可变状态（P1-08、P2-19、P2-20、P2-27、P2-29）

- 依赖进程 CWD，并且在切目录时不失效缓存；
- 生产入口里跑测试、写死 `D:\Test\MTE`；
- 启动器的项目列表写死 JSON；
- 字体路径写死 `c:\Windows\Fonts\msyh.ttc`（`RenderUI.cpp:225` 附近）。

**建议**：引入一个"运行时上下文"（`EngineConfig`），只允许两处写、其余只读：命令行解析处 + 项目打开处。所有路径通过 `EngineConfig::ProjectRoot()` 拼，禁止任何模块直接调 `GetCurrentDirectoryW` / 写死盘符。

### 5. 增量构建的"确定性"没建立（P1-01、P1-04、P2-21、P2-22、P2-34）

`MagicHeaderTool` 是整条构建链上最关键的自研工具，目前有三个正确性缺口：

- **不确定**：`ClassId` 来自 `std::unordered_set` 的遍历顺序 + 进程内自增（`GenerateObjectMetadata.cpp:341-344, 400`）；`GetClassHas` 来自 `std::hash<std::string>`（实现相关）。同一份代码在不同机器/不同编译器上可能生成不同的 id —— 一旦这些 id 落进序列化数据，资产就跨机器不可读。
- **不完全**：增量只看源码 mtime，不看产物（P1-04）。
- **不安全**：N² 并发写同一文件 + 异常逃逸（P1-01、P1-02）。

**建议**：

1. `ClassId` / `ClassHash` 改成**由类名确定性推导**（如 FNV-1a 64 位或 SHA-1 截断），彻底摆脱遍历顺序与工具链；
2. 生成的 id 表额外输出一份 `.idmap.json`（类名 → id），作为**可 diff、可 review** 的产物纳入版本管理；id 冲突在生成期直接报错；
3. 增量判断用"输入哈希（源码内容 + 工具版本 + 参数）→ 输出文件存在且哈希匹配"，不要用 mtime（mtime 在 git 操作、备份恢复、`CreateFile` 篡改下都不可靠）；
4. 写文件统一"临时文件 + 原子替换"。

### 6. 没有质量保障回路（P1-15、P1-02、P0-02）

- 测试只有 1 个文件 3 个用例，且其中 1 个用例与实现矛盾（红的）；
- `add_test`/`ctest` 没接，测试从不执行；
- 没有任何形式的 CI / 冒烟脚本（例如"启动编辑器 3 秒后截图"）。

至少补三类测试，它们正好能抓住本报告里的高危项：

| 测试 | 能抓住 |
| --- | --- |
| `ObjectSystem`：注册 3 个 → 删中间 → 再删尾部 → 断言计数与句柄一致 | P0-02 |
| `BufferManager`：注册纹理 → 断言 Getter 返回的指针与 `ComPtr` 一致（用 `AddRef` 计数验证） | P0-01 |
| `MHT`：连续跑两遍，断言生成的 `.h` 逐字节一致 | P1-01、确定性 id |

### 7. 平台与图形 API 的表述超前于实现（README、Launcher）

- README 声明"仅 Windows x64"，但代码里的 `__underlying_type`、`__pragma`、`Win32Application` 全是 MSVC/Win32 专有 —— 这不是问题，问题是**没有在代码层面显式约束**（缺少 `static_assert(sizeof(void*) == 8)`、缺少 `#ifdef _MSC_VER` 的明确报错）。
- Launcher UI 里有 "DX12/DX11" 选项，但 `RenderCore` 里只有 DX11 设备创建路径 —— 选择 DX12 会走到不存在实现的分支（有用户会以为支持）。
- README 列了 `Vulkan SDK`、`DirectXShaderCompiler`、`SPIRV-Cross`，但当前代码没有引用任何 Vulkan 或 DXC 的入口 —— 属于"依赖表超前于实现"。

**建议**：要么把选项做成"占位并置灰 + tooltip 说明未实现"，要么从 UI 里去掉；README 的依赖表标注"已使用 / 预留"。

### 8. 文档与脚本漂移（P3-13、P3-14）

`README` 里的 `GenerateVSProject.bat` 不存在、`ThirdParty` 目录位置写错、`Build.bat` 不清理 VS 缓存、`CMakeLists.txt` 注释与实际不一致。
**建议**：把 `README` 的"构建"章节当成**可执行脚本的说明**来维护——每加一个 `.bat` 就同步改 README，并在 CI 里加一条"README 提到但仓库不存在的文件"检查（非常便宜）。

## 三、几个需要你决策的问题

这几处不是 bug，而是设计取向，改法差别很大，建议先定方向再动手：

1. **`ObjectSystem` 要不要保留"数组 + 索引"的结构？**
   如果未来需要"遍历全部对象"（序列化整个场景、GC、调试面板），现在的 `vector + swap` 是行不通的，建议直接换成 `unordered_map<id, object*>` + 稳定 id；如果永远只需要计数，那至少要修 swap 的句柄同步。

2. **异常还是错误码？**
   当前 IO 层全是异常。如果倾向"错误码/`expected`"，改动面很大（几十个调用点），但换来的是"任何失败都可控"。如果倾向"保留异常"，那么第 1 批里的框架边界就是唯一防线，必须做扎实。

3. **DX12 是计划内的吗？**
   如果是，`RenderCore` 现在这种"全局 `RenderContext` 单例 + 直接 DX11 类型"的结构基本要重做（`BufferManager` 的接口里到处是 `ID3D11*`）。如果短期不做，建议把 UI 里的选项去掉，避免给使用者错误预期。

4. **`MSVC` 专有依赖要不要清？**
   `__underlying_type` / `__pragma` / `DISABLE_DLL_WARNINGS` 这几处清理成本很低（半天），清掉之后至少 `clang-cl` 能编，对 IDE 体验和静态分析都有好处。要跨平台则需要更大投入。

## 四、本次审查的边界（请一并知悉）

- 全部结论来自**静态阅读**，没有编译、没有运行、没有跑测试。因此"必然崩溃"类结论（P0）我给了触发条件；如果实际运行中未复现，请按正文描述的条件去构造。
- 没有覆盖 `Engine/ThirdParty` 的第三方库本体（ImGui、cereal、ufbx、Lua、nlohmann 等），也没有审计 `Engine/Content` 下的资源。
- 没有做性能实测（P2 里的性能条目是基于代码结构的判断，不是测量结果）。若要量化，建议先用 `RenderDoc` 抓一帧 + `Very Sleepy`/`ETW` 采样，再决定优化优先级。
- 行号以当前工作副本为准；改动后再引用请以正文代码摘录为准。
