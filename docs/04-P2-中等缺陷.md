# P2 中等缺陷

共 35 条。特征：不会必然崩溃，但会给出错误结果、在边界条件下崩溃、或者长期腐蚀性能与可维护性。按模块分组。

## Core：对象与内存

### P2-02 实例 ID 生成器不是原子操作

- **`Core/Core/Public/Object.h:209-212`**

```cpp
static uint64_t GetNextId() { static uint64_t counter = 0; return ++counter; }
```

`Object()` 构造函数里调用（`:190`）。`JobSystem` 确实存在，一旦多线程各自 `ObjectFactory::Create`，`++counter` 就是数据竞争（UB，且可能给出**重复 id**）。重复的 `instance_id` 会让 `ObjectSystemHandle::operator==` 误判"同一个对象"。

修复：`static std::atomic<uint64_t> counter{0}; return counter.fetch_add(1) + 1;`

### P2-33 生成的析构函数无条件注销，绕过工厂就破坏登记表

- **`Programs/MagicHeaderTool/.../GenerateObjectMetadata.cpp:109-119`**

```cpp
code << "    CLASS_NAME() : Core::Object() { /*Please use a factory class to create this object */ ... }";
code << "    ~CLASS_NAME() { this->ObjectUninit(); }";
```

构造函数里 `this->ObjectInit()` 是**被注释掉的**，析构函数却实打实调用 `ObjectUninit()`。于是"用工厂创建"这条约束只写在注释里，靠人守；守不住就会命中 P0-02 的第 3 条（用 `{0,0}` 句柄删别人的槽位）。

修复：把注册放进构造函数（或让 `Object` 基类构造函数自动注册），生成的析构函数改成 `if (IsRegistered()) ObjectUninit();`。同时给生成的析构函数补 `override`。

### P2-21 反射成员按"下一个 class 的起始行"划分

- **`Programs/MagicHeaderTool/Private/BuildPipeline/FindClassMember.cpp:277-285`**

```cpp
size_t ClassStartLineNum  = MagicClass.lineNum;
size_t ClassMaxEndLineNum = NextMagicClass != nullptr ? NextMagicClass->lineNum : -1;
if (VariableLineNum > ClassMaxEndLineNum || ClassStartLineNum > VariableLineNum) { /* 不属于当前类 */ }
```

用一个"下一个 `MCLASS` 出现在第几行"的区间来归属成员。同一头文件里若有**两个以上** `MCLASS` 类、或者有嵌套类/内部辅助类带 `MMEMBER`，成员就会串到前一个类里。现在的代码大多是一个头文件一个类，所以还没暴露；这是随代码增长必然踩的坑。

修复：改用真正的括号匹配扫描（记录 class 的 `{` 位置、按 `{}` 深度出栈），而不是行号区间。

### P2-22 `GENERATE_BODY` 的第二个参数完全不校验

- **`GenerateObjectMetadata.cpp:289-324, 375-381`**

```cpp
std::vector<LocalValidateParameter> TargetParameter = {
    {MagicEngineClass.className, true},   // 会校验
    {"ObjectType", false},                // consistent=false → 不校验
};
```

而 `ValidateParameters` 里 `consistent == false` 的分支是空的（`:318-320`，只有一个注释）。第二个参数最终会被原样拼进 `Core::ObjectType::OBJECT_TYPE`，所以拼错（例如 `Shap` 而不是 `Shape`、大小写错）不会在这里报错，而是等到编译生成文件时报一句"`Shap` 不是 `Core::ObjectType` 的成员"——错误信息指向 `out/` 里的生成文件，排查成本很高。

修复：把 `ObjectType` 的合法值集合（`Unknown/ENGINE/PROJECT`）传进来做枚举值校验。

### P2-31 `JobSystem::Uninstall` 丢弃队列任务、`GetWorkerCount` 空指针

- **`Core/Jobsystem/JobSystem.cpp:69-80, 192-195`**

```cpp
void JobSystem::Uninstall() {
    running = false;   // worker 外层 while(running) 立刻结束，队列里没跑的任务全部丢弃
    ...
}
```

- 关闭时队列里剩余任务被**静默丢弃**，调用方以为 `ScheduleBatch` 的任务都会执行。
- `GetWorkerCount()` 直接 `m_pool->GetWorkerCount()`，没有空判 → 在 `Init()` 之前（或 `Uninstall()` 之后）调用即空指针解引用。启动早期/关闭晚期调用它做日志统计就会崩。
- `Uninstall` 也没有 `m_pool.reset()`、没有清空 `queue`，重复 `Init()` 会泄漏上一批线程对象。

修复：`Uninstall` 里先 `queue` 排空（或明确记一条"丢弃 N 个任务"的日志）再关线程；所有对 `m_pool` 的访问加空判；`Uninstall` 末尾 `m_pool.reset()`。

### P2-32 "异常让 worker 线程终止"的注释是错的

- **`Core/Jobsystem/JobSystem.cpp:180-185`**

注释写 "let them propagate"，实际语义是 `std::terminate()` — 异常逃出 `std::thread` 入口不是"线程结束"，而是**整个进程结束**。这条注释会误导后续开发者在任务里随便 `throw`（P1-02 就是这么来的）。

修复：注释改成事实，并在 worker 循环里包 `try/catch`。

## Core：IO / 路径

### P2-07 `ReadAllText` 不剥 BOM

- **`Core/IO/FileManager.cpp:38-47`**

按二进制整体读入，不做任何处理。Windows 上"记事本另存为 UTF-8"默认带 BOM（`EF BB BF`），此时 `JSON::parse` 在第一行就抛 `parse_error`。项目自身的 `project.json`、语言包、`engine_headers.buildmeta` 都是这条路径，用户手改一次配置就可能导致项目打不开（叠加 P2-10 直接崩）。

修复：读到内容后判断前 3 字节是否为 BOM，是则剥掉；或者统一提供 `ReadAllTextNoBom`。

### P2-08 `WriteAllText` 不校验写入结果

- **`Core/IO/FileManager.cpp:73-80`**

```cpp
file.write(content.data(), content.size());   // 没有 if (!file) 检查
```

对比同文件里 `WriteAllBytesImpl`（`:16-19`）**有** `if (!file) throw`。同一个 IO 层两种行为：磁盘满 / 路径变只读时，`WriteAllBytes` 报错而 `WriteAllText` **静默成功**。`GenerateMetadataFile` 用的正是 `WriteAllText` —— 于是"生成成功但文件是空的"这种情况不会被发现。

修复：统一走一个 `WriteAllBytesImpl`，末尾检查 `file` 状态。

### P2-34 `CreateFile` 篡改已存在文件的 mtime

- **`Core/IO/FileManager.cpp:162-171`**

```cpp
if (fs::exists(p)) { fs::last_write_time(p, fs::file_time_type::clock::now()); return true; }
```

"创建文件"这个语义下，对**已存在**文件刷新 mtime 完全出乎预期。MHT 的增量判断正好以 mtime 为准（P1-04），这条会让基准被无故污染；若 `p` 实际上是**目录**，`last_write_time` 还会抛异常。

修复：`CreateFile` 只做"不存在则创建"，已存在直接 `return true`；"touch" 语义另外开一个函数。

### P2-05 `MoveFile` 先删目标再改名

- **`Core/IO/FileManager.cpp:173-190`**

```cpp
if (fs::exists(dstPath) && fs::is_regular_file(dstPath)) fs::remove(dstPath);
fs::rename(srcPath, dstPath);
```

`rename` 失败（跨盘、目标被占用、路径过长）时，**目标文件已经被删掉了**，源文件还在——一次"安全的移动"变成了"删掉用户的文件"。且整个函数 `catch(...)` 全吞并只返回 `false`，调用方无法知道失败原因。

修复：先 `fs::rename`，失败再降级为"copy + 删除源"（跨盘场景）；错误至少记日志并返回 `error_code`。

### P2-06 用 `path::string()` 取文件名

- **`Core/IO/FileManager.cpp:232-244`**

```cpp
for (const auto& entry : fs::directory_iterator(dir))
    files.push_back(entry.path().filename().string());
```

`path::string()` 返回窄字符，Windows 上是 `char`；非 ASCII 文件名（中文资源）会乱码或抛 `filesystem_error`（宽度转换失败）。`directory_iterator` 也是抛异常重载。

修复：内部一律用 `wstring`，只在**显示**时 `ToNarrowString`；遍历用 `error_code` 版本。

### P2-35 文件浏览器路径校验可绕过

- **`RenderEditor/Private/Editor/GUI_FileBrowserUI.cpp:313-317, 386-397`**

```cpp
std::wstring relative = currentPath;
if (relative.starts_with(L"Game/") || relative.starts_with(L"Game\\")) relative = relative.substr(5); // 硬编码跳过 5 个字符
```

- `IsUnderGameFolder` 只做 `lexically_normal` 之后的前缀比较 → `Game\..\..\Windows` 归一化后确实不在 `Game` 下，但**输入校验发生在归一化之前的路径拼接**，中间状态可绕过；同时 `Game`（不带分隔符）也会被 `starts_with` 判成"在 Game 下"。
- `substr(5)` 把"前缀长度"写死，`Game` 与 `Game\` 两种形式靠后面 `:392-394` 再补删一个分隔符来兜，任何前缀变化（改成 `Content\`）都要连带改两处。

修复：用 `fs::weakly_canonical(root / relative)` 与 `fs::weakly_canonical(root)` 做**真前缀**比较（比较路径分量，不是字符串），并由一个常量统一管理前缀。

## Core：日志

### P2-11 日志轮转未实现：`maxSizeMB_` 是死代码

- **`Core/Logger/Private/LoggerImpl.cpp:19`**、**`Core/Logger/Internal/LoggerImpl.h:44`**

```cpp
maxSizeMB_ = 100; // 100MB    ← 全项目仅此一处出现（赋值，从不读取）
```

`maxSizeMB_`、`checkIntervalSec_` 都被声明并在 `Init` 里赋值，但 `maxSizeMB_` **没有任何读取点**。所谓"100MB 滚动"实际不存在：

- 后台线程只做"每 5 秒 `FlushToFile`"，日志文件只增不减；
- 一个开着编辑器跑一整天、且错误日志被 P1-05 那种"每帧刷错误"的场景点着的会话，可以把磁盘写满；
- 文件名按"精确到秒"生成（`:28`），也就是说**每次启动一个新文件**，旧文件永不清除 → 目录里堆积无数小文件。

修复：在 `FlushToFile` 里检查 `fs::file_size(currentLogPath_) > maxSizeMB_ * 1MB` 就切新文件；启动时清理超过 N 天/N 个的旧日志。

### P2-12 刷盘不持锁，与写入线程竞争同一个 `vector`

- **`Core/Logger/Private/LoggerImpl.cpp:146-161`**

```cpp
void LoggerImpl::FlushToFile() {
    //std::lock_guard<std::mutex> lock(fileMutex_); 不持有锁
    if (buffer_.empty()) return;
    for (const auto& line : buffer_) allLines += line + "\n";
    IO::AppendText(currentLogPath_, allLines);
    buffer_.clear();
}
```

`buffer_` 的写入点在 `:72`（`LogImpl`，持 `Mutex_`），读取/清空点在 `:148-160`（后台线程 + `Uninstall`），**两把锁不是同一把**（`fileMutex_` 被注释掉了）。对 `std::vector` 的并发 `push_back` / 遍历 / `clear()` 是数据竞争（UB）：轻则丢行（这正是"日志偶尔少几条"的原因），重则迭代器失效读到已释放内存。

> 备注：这条的实质严重度偏 P1（UB 可能崩），只因发生在日志路径、且后果多为丢行，暂列 P2。修的时候请顺手把 `FlushToFile` 改成"持锁 swap 出本地副本，锁外写盘"，这样既不丢行也不阻塞写入。

同时注意 `AppendText(currentLogPath_, ...)` 每次刷盘都**重新打开/关闭**文件（`:108-115`），高日志量下这本身就是不小的开销。

## Core：Lua

### P2-03 Lua 分配器释放时不扣减统计

- **`Core/Private/LuaVM/LuaVMImpl.cpp:56-84`**

```cpp
if (nsize == 0) { free(ptr); return nullptr; }   // 没有 m_totalAllocated -= osize
```

`m_totalAllocated` 只增不减，任何"看 Lua 占多少内存"的诊断都失真。另外 `realloc` 失败时（`result == nullptr`）也照样执行了"减旧加新"，此时内存根本没变。目前它还只是统计用途，所以列为 P2；但一旦用它做内存预算/GC 触发就会变成 P1。

修复：`nsize == 0` 时 `if (allocator) allocator->m_totalAllocated -= osize;`；`realloc` 失败时不动计数。

### P2-04 拼接 Lua 源码时不做路径转义

- **`Core/Private/LuaVM/LuaVMImpl.cpp:176-198`**（`RegisterPackagePath`）

```cpp
script += "package.path = package.path .. \";" + path + "\"\n";   // 大致形式
```

Windows 路径天然含 `\`：`\P` 在 Lua 字符串里是非法转义序列，`\\` 会变成单个 `\`，`\t`/`\n` 会被解释成制表/换行。也就是说**现代码在 Windows 上要么直接语法错误，要么悄悄把路径改坏**。路径里出现 `"` 还能直接注入任意 Lua 代码。

修复：

```cpp
lua_getglobal(L, "package"); lua_getfield(L, -1, "path");
lua_pushlstring(L, path.c_str(), path.size());
lua_concat(L, 2);
lua_setfield(L, -2, "path");
lua_pop(L, 1);
```

用 Lua C API 拼值，永不拼源码；确实要拼源码时必须做完整转义。

## RenderCore / RenderRT

### P2-13 `UpdateBuffers` 无锁遍历纹理表

- **`BufferManagerImpl.cpp:184-243`**

注册路径是 `std::lock_guard` 保护后 `push_back`（`:146-148`），而 `UpdateBuffers` 在 `:193` 直接遍历 `buffers.textures`。若渲染线程正在缩放窗口、加载线程同时注册纹理，`vector` 扩容会让迭代器失效 → 读写随机内存。

修复：`UpdateBuffers` 全程持同一把锁，或者 `swap` 出一份快照在锁外处理（后者性能更好）。

### P2-14 所有 Getter 都是线性查找 + 裸指针

- **`Internal/BufferManagerImpl.h:17-26`**，`BufferManagerImpl.cpp:247-305`

```cpp
#define GET_BUFFERS_FUNCTION(target,type,get,getType) \
for (unsigned int i = 0; i < buffers.type.size(); i++) { \
    auto& buffer = buffers.type[i]; \
    if (buffer.Name == (target)) return buffer.get.getType(); }
```

- 每次 `GetBuffer("xxx")` 都是字符串比较的线性扫描；渲染热路径上每帧多次调用 → O(对象数 × 调用次数)。
- 返回裸指针且不加锁，Get 与注册并发即数据竞争。
- 名字用 `std::string` 按值传参（`:247` 等全部签名），每次调用都构造 string。

修复：注册时建 `unordered_map<std::string, index>`；所有 API 改成 `const std::string&` 或 `std::string_view`；Get 加读锁或改用不可变快照。

### P2-15 `RegisterBuffer` 对 `context.Desc` 无空判

- **`BufferManagerImpl.cpp:44-50`**

```cpp
buffer.Desc = *context.Desc;                                     // 先解引用
RenderContext::Get().g_pd3dDevice->CreateBuffer(context.Desc, ...);
```

对比 `RegisterTexture2DBuffer` 明明考虑了 `context.Desc != nullptr`（虽然是先解引用后判空，见 P1-05）。两条路径的空判策略不一致，`Desc` 为空时直接崩溃。

修复：入口处 `if (!context.Desc) { ErrorCapture{}(...); return; }`，并且把"可变参数结构体"改成值传递，避免调用方传局部变量地址。

### P2-16 视图尺寸用函数内 `static` 保存

- **`RenderRTImpl.cpp:108-128`**

```cpp
static int static_width = 0; static int static_height = 0;
static Debouncer debouncer(500, [&](){ LOG_INFO(...static_width...); });
```

函数级 `static` 是**进程级单例**。只要有第二个渲染目标/第二个交换链，或未来做多窗口，它们会共享这一份"上次尺寸"，导致 `UpdateBuffers` 被错误跳过或重复触发。`debouncer` 的 lambda 还捕获了 `this` 之外的引用，析构顺序也无保障。

修复：搬进 `RenderRTImpl` 的成员变量。

## Editor / RenderUI

### P2-01 命令合并成功时不清空 redo 栈

- **`RenderUI/Private/Command/CommandManagerImpl.cpp:42-51`**

```cpp
if (合并条件) {
    m_undoStack.back()->MergeWith(command.get());
    return;      // 没有清空 m_redoStack
}
```

标准语义：任何新命令（无论是否合并）都必须让 redo 栈失效。这里合并走的是提前返回，redo 栈被保留 → 用户"撤销 → 新操作 → 再重做"会拿到**基于旧状态**的操作，导致撤销链与文档状态不一致（表现为"重做后内容叠加/错位"）。

修复：合并分支里同样 `m_redoStack.clear()`。

### P2-17 `WM_MOVE` 用 `LOWORD/HIWORD` 解析坐标，丢失符号位

- **`RenderEditor/Private/Windows/WindowHandler.cpp:41-49`**

```cpp
int newX = LOWORD(lParam);   // 无符号 16 位
int newY = HIWORD(lParam);
Win32Application::Get().WondowsConfig->WindowsPostion = int2(newX, newY);
```

窗口被拖到主显示器**左侧**（坐标为负，例如 `-1200`）时，`LOWORD` 得到 `64336`，存进去的"窗口位置"完全错误。随后 `CleanupWindows` 里"越界就重置到 `(100,100)`"的判断（`Win32Application.cpp`）就会把窗口位置重置掉——多显示器用户每次开编辑器窗口都跳回左上角。

修复：用 `GET_X_LPARAM(lParam)` / `GET_Y_LPARAM(lParam)`（含 `<windowsx.h>`），它们返回有符号 `int`。顺带把 `WM_SIZE` 里的 `LOWORD/HIWORD` 换成 `GET_X_LPARAM/GET_Y_LPARAM`（尺寸虽非负，但语义统一更好）。

### P2-18 `WM_DESTROY` 先销毁设备，后关 ImGui 后端

- **`RenderEditor/Private/Windows/WindowHandler.cpp:50-53`**；`Editor/Private/Windows/Win32Application.cpp:149-152`

`WM_DESTROY` 里立刻 `CleanupDeviceD3D()`，而 `ImGui_ImplDX11_Shutdown()` 发生在主循环之后的 `EndUI()`。关闭阶段 ImGui 会去释放/查询已经销毁的设备相关对象 → 关闭时的偶发崩溃或 GPU 验证层报错。

修复：`WM_DESTROY` 只 `PostQuitMessage`，设备与 UI 全部在 `wmain` 的收尾里按"UI → 设备"顺序统一销毁。

### P2-19 生产入口跑测试代码，并硬编码 `D:\Test\MTE`

- **`Editor/MagicEditor/Private/Main.cpp:99`**（`TestAdd()`），`:13-43`

```cpp
void TestAdd() { ... IO::CreateDirectory(L"D:\\Test\\MTE\\TEST"); ... }
...
TestAdd();            // 每次启动都执行
```

- 产品代码里执行测试逻辑，每次启动都会在**用户 D 盘**创建目录/写文件；D 盘不存在或只读时行为不可预期。
- 它不经过 `ObjectFactory` 的路径还会命中 P2-33 的"绕过工厂"问题。
- `FreeConsole()`（`:101`）在 `Run()` 之前，配合双入口（`wmain`/`WinMain`）会出现"GUI 模式下没有控制台却仍在写 stdout"的情况。

修复：整段删除，或挪进 `Tests/` 并只在该测试目标里编译。

### P2-20 失败也返回 0

- **`Editor/MagicEditor/Private/Main.cpp:94`**、`Programs/MagicHeaderTool/Private/Main.cpp:16-18`

```cpp
if (!error.error) { ...; return 0; }              // 初始化失败 → 退出码 0
if (!parser.parse_check(argc, argv)) return 0;    // 参数错误 → 退出码 0
```

`Build.bat` / CI / IDE 都靠退出码判断成败。MHT 在 `--generate-dir` 缺失（`cmdline` 的 required 参数）时返回 0，构建脚本会认为"生成成功"然后编译失败，把问题推到下游。

修复：失败统一 `return 1`（或用 `EXIT_FAILURE`），并保证 `--help` 这类正常退出走 `return 0`。

### P2-25 `Checker.h` 依赖传递包含

- **`Core/Core/Public/Common/Checker.h:3-8, 64-69`**

```cpp
#include <cassert>
#include <type_traits>
#include <stdexcept>
...
inline std::string HrToString(HRESULT hr) { char s_str[64]; sprintf_s(...); return std::string(s_str); }
```

用了 `std::string`、`sprintf_s`，但既没含 `<string>` 也没含 `<stdio.h>/<cstdio>`。目前能编译只是因为 `windows.h` / 其他头先被包含。头文件顺序一变就编译失败——这是"能编过但很脆"的典型。

修复：补齐 `<string>`、`<cstdio>`；同时把 `using HRESULT = long;` 这类**全局类型别名**移进 `Core` 命名空间（见 P3-03）。

### P2-23 向量 `operator<` 用 `&&` 组合分量

- **`Core/Core/Public/Common/Math.h:113-132`**

```cpp
friend bool operator<(const Vec2& a, const Vec2& b) { return a.x < b.x && a.y < b.y; }
```

"两个分量都更小"既不传递也不完全，**不满足严格弱序**。放进 `std::map`/`std::set`/`std::sort` 是 UB（可能死循环、可能丢元素）。调用方看起来只想比较大小，结果得到的是"支配关系"。

修复：要么改名成 `Dominates(a, b)`，要么实现词典序 `<`（`a.x != b.x ? a.x < b.x : a.y < b.y`）。

### P2-24 `Math.h` 取消 `min/max` 宏，`TextLayout.h` 却依赖裸 `max()`

- **`Core/Core/Public/Common/Math.h:13-15`** vs **`RenderUI/Public/Tools/TextLayout.h:201, 212, 214`**

```cpp
// Math.h
#undef min
#undef max
```

```cpp
// TextLayout.h
result.totalWidth = max(result.totalWidth, width);
result.baseLineHeight = max(font->CalcTextSizeA(...).y, result.fontSize);
```

`#undef` 之后，`TextLayout.h` 里的 `max(...)` 只有在**先**包含了 `<algorithm>`（提供 `std::max` 不会自动生效，因为这里是无限定调用）或者某处有 `using namespace std` 时才能解析。当前能编过纯属包含顺序巧合；顺序一变就是"`max` 未定义"或"调用到 `Windows` 的宏"。

修复：`TextLayout.h` 里显式写 `std::max`，并加 `#include <algorithm>`。

### P2-26 运行时给已构建的字体图集追加字体

- **`RenderUI/Public/Tools/TextLayout.h:104-137`**

```cpp
ImFont* font = ImGui::GetIO().Fonts->AddFontFromFileTTF(normalizedPath.c_str(), 18.0f, &config);
```

`AddFontFromFileTTF` 只是在图集里登记字体配置，**真正的纹理烘焙发生在 `ImGui_ImplDX11_CreateDeviceObjects()`（即 `Build()`）**。在 GUI 运行期间调用它，新字体不会拿到新的纹理页：字形要么完全不显示，要么显示成上一页的乱码区域。日志面板里"给不同文件类型用不同字体"这类需求就会命中。

修复：要么在 `Init` 阶段把需要的字体一次性注册好（推荐，字体路径做成配置表），要么调用后触发图集重建（`Fonts->Build()` + 重建设备对象，代价高、不适合每帧路径）。

### 补充：文件列表每帧做全文排版（性能）

- **`GUI_FileBrowserUI.cpp:211-240`、`IMGUI_LoggerUI.cpp`**

文件列表对每个 item 都构造 `TextLayoutParams` 并调用 `LayoutText`（内部有字体缓存查找 + UTF8 解码 + 逐字符宽度计算）。目录里 200 个文件时就是 200 次排版/帧。目前可用的缓解是"只有一个 `GetFontCache` 里的命中"，但逐字宽度计算仍在。

修复：按 `(text, font, size, wrapWidth)` 缓存 `TextLayoutResult`，仅在文本或宽度变化时重算。

### P2-29 对临时 `std::wstring` 取 `c_str()` 后跨语句使用

### P2-30 AssetPipeline：`map::at` 抛异常 + FBX 导入是空实现
